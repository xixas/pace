Always know if your billed hours are on pace

A small desktop app that shows each person their week (billed hours against the 8.5 h/day target and the loss-of-pay line) and their month (per-project targets like Tweelin 140 h) in the panel at all times. It reads hours from PineStem and leave and holidays from DhiHRMS, and nudges them before a shortfall is still fixable.

Today

The pinestem-billing-report skill gives an on-demand check for Vikas only. It ignores leave and holidays and hard-codes 42.5 h.

Target

Anyone installs one app and signs in once with Microsoft. From then on the panel always shows 30.1 / 42.5 h with a colour, and a notification arrives when pace slips.

Done when

A KDE user, a Windows user and Vikas on GNOME each see week and month numbers that match PineStem to 0.01 h, with leave applied, within 0.3 s of login.

What a user actually does

Setup takes three clicks and needs no passwords, tokens or config files. Everything after that is passive: the number sits in the panel and the app speaks up only when it matters.

Architecture: DhiHRMS is the only door

hrms-api already calls PineStem with org-level credentials and maps each employee to a PineStem user (common/pinestem/pinestem.client.ts:185 getEmployeeDetailedBilling → FilterBillingDetails_New). It also owns the leave, holiday and comp-off calendar (common/calendar/working-calendar.ts). So the app talks only to hrms-api, signs in with Microsoft, and never sees a PineStem password.

New: my-hours

?from=2026-10-01&to=2026-10-31 returns one row per day per project, {date, project_code, project_name, billable_min, non_billable_min}. It is built on the existing getEmployeeDetailedBilling, with single-day aggregation done server-side to avoid the unstable ORDER BY Date paging trap.

New: my-days

The output of working-calendar.ts for a date range: off days, holidays, opted-in RH only, approved leave with half-days, comp-off and joining date. This fixes the my-lop gaps (it counts pending leave, counts RH it shouldn't, and leaves crossing weeks get double-counted).

New: my-targets

Returns per-employee daily floor/ideal and per-project monthly hours, as set by the lead in hrms-portal. Org defaults come from lms_pdr_metric_config (8.5 h) and the LOP config (9 h / 5 h). Phase 1 can skip it and use local settings.

GNOME extension (pace@osmosys, GTK/Adwaita look, cloned from claude-usage@vikas) reads status.json only. It makes no network calls and needs no second login. The app runs headless underneath it.
Why not have the app log in to PineStem directly? It would mean 20 passwords in keyrings and a password re-sent every 120 min, because there's no refresh endpoint (12 audit rows per user per day). PineStem SSO needs a public-client registration that doesn't exist yet. hrms-api already solved this.

Pace math: three lines, not one

The week bar carries three markers, because the company actually uses three numbers. The LOP line is the hard one: hrms-api counts worked days as floor(total/9) + (remainder ≥ 5 ? 1 : 0) (modules/billing-report/lop-calculator.ts:36-48). So a full 5-day week is LOP-safe at 41 h, not 42.5. Thresholds come from /billing-report/config/ and are never hard-coded.

Week verdict (continuous, no gaps)

need = (target − logged_before_today) ÷ remaining_days_incl_today

  • AHEAD logged ≥ expected-to-date
  • ON TRACK need ≤ 9.0 h/day
  • TIGHT 9.0 < need ≤ 10.5 h/day
  • AT RISK need > 10.5, or the LOP line is unreachable at 10.5 h/day
  • SHORT week over and under target (shows LOP days if under the LOP line)

Today's partial hours count toward logged but aren't treated as a shortfall until 23:59, because billing is often entered later.

Month per project

eff_target = target × avail_days ÷ month_working_days (proration toggle, on by default)

expected_to_date = eff_target × elapsed ÷ avail_days

need/day = (eff_target − billed) ÷ remaining avail_days

Billable minutes only, so non-billable doesn't count toward a client target. Same verdict bands, scaled by that project's share of the day.

Example, Oct 2026: 22 weekdays − 2 holidays (illustrative) = 20. With one leave that's 19, so Tweelin 140 → 133 h.

Screens

All mocks use one example: Thursday 29 Oct 2026, 14:10. Mon–Wed billed 9.2 + 8.4 + 9.0, today 3.5 so far, and the week is on track. October Tweelin is 112.5 of an effective 133 h, so the month is behind. Each desktop gets its native idiom. The same Rust core feeds all of them.

Stock GNOME without the AppIndicator extension still works for anyone who installs this extension. With neither, the mini widget and notifications are the fallback.

A 230 px frameless window you can drag anywhere. It remembers its position and opens at login if enabled, which makes it the "see it all the time" surface on desktops whose tray hides labels.

Limit: keep-on-top is a no-op on GNOME and KDE Wayland, which have no protocol for it. The widget sits on the desktop like a sticky note, and KDE users can pin it with a window rule. On Windows, macOS and X11 it can float on top.

It's a webview, so it loads only while shown and stays under 25 MB.

Stack, speed budget and build order

Stack

Tauri v2 (pin 2.12.4; 2.12.5 is 5 days old) for one Rust core and native tray, notifications, autostart and updater on all four platforms, using the system webview (no bundled Chromium).

Rust core: reqwest, serde, chrono, keyring (v4.2.0 is from 2026-08-29, so it's old enough). UI: Svelte + plain CSS styled to look like libadwaita, built with pnpm.

GNOME extension: GJS ESM for Shell 48–50, forked from claude-usage@vikas.

Packages: GitHub/GitLab CI builds .deb, .rpm, AppImage, .msi and .dmg. Flathub later.

Speed budget (hard requirements)

  • Idle means tray only, with no webview loaded. Windows are created on click and destroyed on close.
  • From cold start to a number in the tray in < 300 ms (cached status.json), with the refresh after that.
  • Idle RAM < 40 MB. CPU ≈ 0 between polls, with one timer and no sidecar.
  • At most 3 GETs per poll. The calendar and targets are cached per day.
  • UI bundle < 200 KB. The GNOME extension makes zero network calls.
  • NVIDIA + WebKitGTK: set WEBKIT_DISABLE_DMABUF_RENDERER=1 to avoid blank windows.
  • hrms-api: my-hours + my-days
  • Pace engine + tests
  • Sign-in + tray + status.json
  • Notifications + autostart
  • Dashboard + targets
  • GNOME extension
  • Mini widget
  • CI bundles + 2 colleagues
  • my-targets + portal UI

Decisions

Each row has a recommendation. Row 3 is the one I'd defend least, because leads setting targets in the portal adds hrms-portal work. Pick per row and press Queue answers, or just say "go".

#DecisionChoiceThe fact that decides it
1Where the app gets hours hrms-api already holds org PineStem creds + the user mapping (pinestem.client.ts:185). Direct login means storing 20 passwords and re-sending each one every 120 min.
2Entra registration hrms-api checks only aud + access_as_user, not the client (microsoft-sso.service.ts:64-71). A separate app gets its own consent screen, logs and revocation.
3Who owns targets "Different people have different requirements" is a lead's call. Local-only means trusting each person to type their own target.
4App framework Windows and macOS users are in scope. GTK on Windows/macOS is second-class, while Tauri is one codebase with native tray/notify on all four.
5Repo home It depends on new hrms-api endpoints and company identity, so it's a company tool, not OSS.
6Name Short, verb-like, reads well in a tray tooltip.
Before slice 1: the hrms-api endpoints are a new feature in Vishnu's repo. The hrms-api session is waiting for your go and will build them TDD there. The "Pace" Entra registration needs an Azure admin.
